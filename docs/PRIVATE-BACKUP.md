# Local private backups (implementation receipt)

Backup is separate from the filtered snapshot used for cloud-agent sharing. A backup intentionally includes private notes and Obsidian settings. It is **not encrypted**; choose a destination whose access and encryption you control. Do not place it in a shared folder without reviewing that folder's access.

In BrainLink Settings, choose an existing destination outside every vault, select an interval, and enable Backup. Enabling makes and SHA-256-verifies the first copy before saving the schedule. Further copies run only while the local BrainLink app process is running. When backup is enabled, the app no longer exits after its ordinary inactivity timeout. Browser closure does not stop the process, but device shutdown or a crashed process does. The optional **Start BrainLink in the background when I sign in** setting installs a managed per-user login entry: Windows Startup-folder launcher, macOS LaunchAgent, or desktop Linux autostart entry. It starts Setup without opening a browser, keeps scheduled backups running after sign-in, and is off by default. BrainLink removes only its own marked entry when you switch the setting off. The normal app icon continues to open Setup. The last attempt is saved in local app state; if it is overdue when BrainLink next starts, a new backup is attempted. There is no guaranteed wake-from-sleep catch-up, remote destination validation, retention/rotation policy, or encrypted archive yet. Linux autostart requires a desktop session; headless servers need a separate service setup.

Each backup gets a new folder with `manifest.json`, vault contents, and—when present—the local BrainLink RSI proposal journal under `artifacts/rsi/ledger.jsonl` and RSI research-discovery settings and receipts under `artifacts/rsi/discovery.json`. The restore preview copies these artifacts to `BrainLink/rsi/` inside the chosen empty recovery folder; it does not automatically replace the live app-data files. These app-data artifacts can contain sensitive user preferences and research topics, so treat the backup as private. The backup excludes `.git` and `node_modules` from vaults, rejects symbolic links, and does not overwrite prior copies. The manifest contains original note paths and vault names and is sensitive. Verification checks copied file sizes and hashes for notes and app-data artifacts. A backup is written into a unique staging folder and renamed to its visible backup name only after the manifest is complete. A handled failure removes its staging folder and leaves earlier backups untouched. A forced process or power loss can still leave a `.partial` staging folder; it is not a valid backup. The UI shows the persisted last attempt, not a complete backup history.

For recovery, open **Restore a backup** in Settings and use **Choose backup folder** and **Choose empty folder** to select the exact source and a separate destination. BrainLink verifies hashes before copying, requires explicit confirmation, and never changes the configured live vaults. Inspect the restored contents before any manual switchover. If the native folder picker is unavailable, enter the complete paths manually. The restore path is for local recovery, not an agent-accessible sharing channel.

Validation: `node --import ./test/_preload.mjs --test test/backup.test.mjs test/startup.test.mjs test/rsi-ledger.test.mjs` covers private-file inclusion, hash detection of corruption, safe restore, RSI journal artifact restore, authenticated RSI UI API, repeat scheduling, ledger tamper detection and concurrent-instance writes, plus generated/removed login entries across Windows, macOS and Linux, including path escaping and protection of unrelated files. Restore source/destination picker routes are authenticated and covered using test doubles; native folder dialog interaction has not been manually accepted in a desktop session. Native login execution is still awaiting per-OS user-desktop acceptance. Symlink rejection test is skipped on Windows hosts without symlink privilege. This is a tested local foundation, **not** a claim of production-ready disaster recovery. Test a real restore on another device and decide encryption, retention, scheduler and support policy before a commercial release.
