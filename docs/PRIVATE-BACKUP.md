# Local private backups (implementation receipt)

Backup is separate from the filtered snapshot used for cloud-agent sharing. A backup intentionally includes private notes and Obsidian settings. Encryption is optional and off by default. Without it, choose a destination whose access and encryption you control. Do not place an unencrypted backup in a shared folder without reviewing that folder's access.

In BrainLink Settings, choose an existing destination outside every vault, select an interval, choose how many copies to keep, and enable Backup. The default **All copies** never deletes old backups. When a finite count is selected, BrainLink removes older copies only after the new copy passes hash verification, and only if each old copy is also a complete verified BrainLink backup whose files exactly match its manifest. Damaged, unknown, symbolic-link, partial, or user-modified folders are left untouched. To encrypt, turn on **Encrypt backup contents**, use **Show or create recovery key**, and save that key in a safe place away from this computer. Only new backups are encrypted; earlier copies are left as they are. BrainLink stores the raw key in per-user local app data for unattended scheduled backups; on POSIX systems it requires owner-only file permissions, while Windows stores it in Local AppData under the current user's profile. Do not delete `backup-key.bin` or encrypted backups will need the separately saved recovery key. The key is never written to the vault, backup destination, or BrainLink config. AES-256-GCM protects file contents, names, vault names and the manifest; backup folder timestamps, file counts, and exact encrypted object sizes remain visible. The local key file protects against someone who only obtains the backup destination, not malware or another process running as the same user. BrainLink cannot recover a lost key. Existing unencrypted backups remain restorable.

Enabling Backup makes and verifies the first copy before saving the schedule. Further copies run only while the local BrainLink app process is running. When backup is enabled, the app no longer exits after its ordinary inactivity timeout. Browser closure does not stop the process, but device shutdown or a crashed process does. The optional **Start BrainLink in the background when I sign in** setting installs a managed per-user login entry: Windows Startup-folder launcher, macOS LaunchAgent, or desktop Linux autostart entry. It starts Setup without opening a browser, keeps scheduled backups running after sign-in, and is off by default. BrainLink removes only its own marked entry when you switch the setting off. The normal app icon continues to open Setup. The last attempt is saved in local app state; if it is overdue when BrainLink next starts, a new backup is attempted. There is no guaranteed wake-from-sleep catch-up or remote destination validation. Linux autostart requires a desktop session; headless servers need a separate service setup.

Each backup gets a new folder with `manifest.json` and named vault/artifact files when encryption is off. With encryption on, it instead contains `manifest.enc` and opaque random-named encrypted objects; decrypted manifest data stays in memory. Both modes include RSI artifacts when present, and restore writes those artifacts to `BrainLink/rsi/` in the chosen empty folder; it does not replace live app-data files. Backups exclude `.git` and `node_modules`, reject source symlinks, and do not overwrite prior copies. A new copy is assembled in a hidden staging folder and published only after all content and its manifest are written. A handled failure removes that staging folder; an abrupt process or power loss may leave a `.partial` folder that is not a valid backup. The UI shows the last saved attempt's local time and whether it was manual, scheduled or created during setup, with a safe fallback for older status records. It does not show a complete backup history unless the user opens Restore.

For recovery, open **Restore a backup** in Settings and choose **Find verified backups**. BrainLink checks up to the 20 most recent backup folders and offers only copies whose manifest and file hashes pass; encrypted copies are checked with the local recovery key. The list hides vault and file names from the manifest. Choose a listed copy and an empty destination, then confirm. BrainLink verifies again before copying and never changes the configured live vaults. Older copies can still be selected with **Choose backup folder**. Inspect the restored contents before any manual switchover. If the native folder picker is unavailable, enter the complete paths manually. The restore path is for local recovery, not an agent-accessible sharing channel.

Validation: backup history and recovery behavior are covered by `test/backup.test.mjs`; key handling, startup, and RSI backup artifacts are covered by `test/backup-key.test.mjs`, `test/startup.test.mjs`, and `test/rsi-ledger.test.mjs`. The encrypted restore test also creates a fresh BrainLink Setup instance with a separate app-data folder, verifies the source key is absent, rejects a wrong key without changing the empty destination, then restores with the exported recovery key. This is a second-install simulation, not a physical second-device test. Restore folder picker routes are authenticated and covered using test doubles; native folder dialog interaction remains unverified. Native login execution is still awaiting per-OS user-desktop acceptance. Symlink rejection is skipped on Windows hosts without symlink privilege. This is local automated evidence, **not** a claim of production-ready disaster recovery. Windows key storage relies on Local AppData ACLs and still needs a native security review. Encryption protects backup copies from someone who only gets the backup destination; it does not protect against malware running as the same OS user. A lost recovery key cannot be recovered.
