# Session-to-memory filing: first governed path

Status: local UI filing, connected-AI close operation, opt-in hook setup and session-end reminders are implemented and locally tested. Live client lifecycle acceptance remains unverified.

The local BrainLink Sessions screen now offers **File summary** when a stored session has a summary. For imported Claude Code and Codex conversations without a client-authored summary, BrainLink creates a short, explicitly unverified excerpt from the original user goal, the latest meaningful user direction, and the final assistant reply. Each part has its own token limit so a long initial prompt cannot hide the ending; low-signal replies such as “continue” are not treated as the latest direction. Secret scanning runs again while assembling the excerpt. This is deterministic text selection, not AI-generated outcome verification.

The user chooses a destination vault and an existing folder in that vault, previews an episodic note, and explicitly saves it. Hidden, protected, excluded, nonexistent and symlinked folders are not offered or accepted. The user may remember the vault and folder for that exact project; BrainLink reuses that choice only while the folder still exists in the same vault. Similar project names never inherit it. The note inherits `private: true` regardless of the session's sharing toggle, carries the session ID and client as provenance, and remains `status: proposed` / `confidence: reported`. It never copies raw turns or promotes a summary to verified semantic knowledge. The note writer rejects credential-like content and never overwrites an existing note. The preview also proposes links to matching notes from the explicitly selected vault's privacy-filtered index; private, generated, excluded and other-vault notes are not candidates. Links are saved only when the user confirms the preview. Suggestions are reviewable associations, not proof that two claims are equivalent.

Connected agents can call `session_filing_folders` after identifying an explicitly enabled vault. It returns only existing, non-hidden, non-protected, non-excluded directories in that scope. `session_close` accepts one exact returned folder path; an invalid path is refused. If omitted, BrainLink reuses an exact saved project folder or a safe same-vault suggestion when allowed, then falls back to the configured intake folder. The close prompt directs agents to choose a clearly relevant existing folder or use intake when none fits, then preview before saving.

The filing screen first reuses a remembered vault/folder for the exact project when that folder still exists. Otherwise it may suggest a folder from an exact note-title mention in the summary, or from multiple matching public notes that cluster in one folder. It searches only the user-selected vault's privacy-filtered index, and abstains when exact mentions are split across folders or the similarity evidence is weak. The suggestion explains whether it came from a saved choice or related notes. It is never an automatic move: the user sees and can change the folder, previews the full note and links, and confirms before saving. A missing, inaccessible, read-only or excluded destination is not suggested. Similar project names never inherit remembered choices.

Connected-AI closeout now reuses a saved destination vault only when the session's exact project identifier matches a route the user previously saved. The AI may omit `vault` in that case; the response names the suggested vault and full preview path. For an unknown or similar-but-not-exact project, the AI must pass an enabled vault or ask the user. A scoped agent cannot use a saved route into another Twin's vault, and the denial does not reveal that vault's name. If the caller omits `folder`, BrainLink checks a saved choice for that exact project, then a strong same-vault note match only when the active Twin has both semantic memory and search permission. Otherwise it uses the configured intake folder. The preview and result include the chosen path and any suggestion reason; confirmation still requires the exact previewed destination and folder. This feature never reads semantic notes for a Twin that cannot search them. Tests use fictional vaults, verify exact project routing, reject fuzzy matches and cross-Twin routing, and retain the private episode and explicit-confirmation behavior.

When an AI includes `source_session_id`, BrainLink now checks that the referenced session exists and is visible under the user's session-sharing choice or the active Twin's session scope. It reads only session metadata for this check, not transcript messages. If `project` is also provided, it must exactly match the source session's stored project. Missing, private, cross-Twin, or mismatched references are rejected before either the private closeout session or note is written. This protects provenance from a mistaken or fabricated session ID; it does not independently verify the AI-reported outcome.

Focused validation on Windows: `node --import ./test/_preload.mjs --test --test-concurrency=1 test/session-close.test.mjs test/session-filing.test.mjs` passed 17/17. This validates the local MCP and filing APIs with fictional vaults; live AI-client closeout and installed desktop usability remain unverified.

This path reuses the existing `proposeNote` write and attribution controls. The local API requires its Setup token. The preview and save actions require a chosen vault; neither an AI client nor filename matching silently chooses a personal, company, or client destination. The UI is available in English, Traditional Chinese, and Portuguese.

Connected MCP clients also have `session_close` and the `close-session` prompt. A client sends a stable task ID, title, goal, actual outcome and optional decisions, actions, corrections, open questions and next steps. It may omit the vault only for an exact project route previously saved by the user; otherwise it supplies an enabled vault or asks the user. A preview writes nothing. After approval or the user's close instruction, `confirm=true` stores a private summary-only session and a private proposed episode in that vault. The closure's client ID is deliberately distinct from imported Codex/Claude Code sessions, so the imported-session sharing switch cannot reveal it. Reusing a task ID is refused rather than changing an earlier outcome. This is an AI-reported summary, not an automatic transcript reader or a verified fact.

The `review-session` prompt provides a guided route for an imported session. It appears to scoped agents only when both session reading and approval-gated closeout are granted. The AI must identify one exact session, obey the user's summary/full-text sharing settings, stop when access is denied or the content is insufficient, select an explicitly allowed vault, and preview the new private episode before asking to save it. The exact source session ID is carried into both the proposed summary and a `source_session_id` frontmatter field for traceability. The prompt does not read data itself, change access settings, or create an automatic background summary.

## Optional local AI summary draft

The Sessions panel can opt in to local summary drafts and set an Ollama model name. By default, the user clicks to make a draft. A separate **Automatically draft after a session ends** setting can make BrainLink check end cues while the app is running and prepare one draft at a time for an exact matching imported Claude Code, Codex, or idle DeepSeek Harness session. It uses the fixed loopback endpoint `http://127.0.0.1:11434/api/chat`, with a bounded set of redacted user and assistant turns; it does not send the session ID, project, title, file paths, or tool output. Auto drafting is off by default. Drafts stay in private BrainLink app data and are labeled unverified.

An additional **Automatically save the private draft to the saved project folder** option is also off by default. It requires local summaries and auto drafting to be enabled, plus a previously saved, exact-project destination whose vault is writable and whose folder still exists. BrainLink does not infer the destination or fall back to the vault intake folder. It checks the exact folder for an existing private episode with the same session source before writing, so repeated scheduler ticks do not file duplicates. The resulting note remains `type: episode`, `private: true`, `status: proposed`, and `confidence: reported`; its local-model text is explicitly unverified. If no exact route exists, the destination is no longer valid, or filing fails, the draft stays in private app data and the UI reports the reason for review. It records the model and draft time. The app's running state is required for background work; this is not an operating-system service that runs while BrainLink is closed. An Ollama service was unavailable on the development machine, so the local model itself has not been exercised; API behavior was tested with fake local responses.

The session and vault note are two separate writes, not a transaction. Close requests hold a cross-process lock on the local session store across the duplicate check, session write and note filing, so concurrent processes cannot overwrite a prior outcome or lose unrelated sessions during persistence. A dead process's lock is reclaimed only when its PID is confirmed absent; malformed or unverifiable locks fail closed. If the session write succeeds but note filing throws, the tool returns `ok: false`, `session_saved: true`, `filing_status: "unknown"`, the saved session ID, and a recovery instruction to open Sessions and use **File summary**. If filing returns without writing (for example, a proposal-only destination), it returns the same recovery fields with `filing_status: "not_written"`. `unknown` is intentional: an I/O error can happen after a file write, so clients must check before retrying. The response does not expose raw filesystem errors. Do not claim both were saved unless `written: true` is returned.

## Correct or withdraw a proposed episode

After filing a session summary in the active `brainlink ui` Setup, the user can open that note, correct its summary, or withdraw the proposal. The user can also reopen the **Find a previously filed summary** panel, choose one vault and explicitly search it; the list returns only matching private proposed episode titles and paths, not summary text, and is capped at 100 results/20,000 scanned Markdown files. The authenticated local route requires the exact session ID, a private `type: episode` note whose `source` matches that session, an enabled writable vault, an included non-symlink Markdown path, and the current full-file SHA-256 etag. Corrections replace only the `## Session summary` section, scan for secrets, and append a dated value-free history entry. Withdrawal changes only `status: proposed` to `withdrawn`; it retains the summary and private note and adds a dated history entry. Neither action edits another session's note or overwrites a stale revision. Discovery is explicit and vault-scoped; no private summary text is loaded until the user opens an item.

The Notes editor supports user correction of an episode body. Saving a changed body appends a dated `Summary corrected` entry to its existing `## Changelog` (or creates that section) and uses the store's full-etag compare-and-swap, so a concurrent edit is not overwritten. For a private BrainLink session episode, frontmatter edits also add a dated `Metadata updated` changelog entry. It lists only a safe allowlist of field names (or just the number of changed fields); it never copies old or new values into the changelog. This history is an application receipt, not a cryptographic audit log, and does not cover edits made outside BrainLink Notes.

For a private note with `type: episode`, `status: proposed`, and a `source` matching `BrainLink session <id>`, the editor offers **Withdraw proposal**. It confirms before acting, changes only the status to `withdrawn`, retains the full summary, private flag and session source, and appends a dated changelog entry. It refuses unrelated sources, non-private notes, non-proposed notes, unsaved edits and stale revisions. Withdrawal does not delete the source session or erase the episode. This is reversible through the ordinary revisioned note editor, subject to vault write permissions.

## End-of-session integration boundary

Both Claude Code and Codex document local `SessionEnd` command hooks. Their hook payloads include a session identifier, working directory, reason, and transcript path. This makes a local end cue technically possible; it does not by itself produce a reviewed outcome summary or authorize saving one. BrainLink must not read transcript contents just because a lifecycle hook supplies a path. The opt-in command below records only a minimal local cue. Transcript ingestion would need a separate explicit setting, source-scope checks, secret filtering, and private-by-default storage.

Add this handler to the client's existing `SessionEnd` hook configuration (merge it with existing hooks; do not replace them):

```json
{
  "type": "command",
  "command": "brainlink session-end-cue --client claude-code"
}
```

The Sessions screen provides **Enable reminders** / **Disable reminders** for each client. Setup merges BrainLink's handler into user-level Claude Code settings or Codex hooks.json, backs up existing files, refuses malformed JSON, and preserves other hooks. Commands use absolute executable, script and application-data paths. Codex must separately review and trust the hook through `/hooks`; the UI labels configuration separately from verified runtime. No trust settings are modified. The `disconnect-all` command used by uninstallers removes only BrainLink's marked handlers.

Use `--client codex` for manual Codex configuration. The command reads hook JSON from stdin, discards `cwd` and `transcript_path`, and writes an idempotent cue under BrainLink's local application data. Reminders appear in the Sessions screen; **Dismiss reminder** hides one while retaining its local record. Duplicate deliveries do not revive dismissed reminders. Before linking reminders, the Sessions screen incrementally refreshes the local import index so a newly ended transcript can appear without restarting BrainLink. Ordinary MCP session listing uses a 15-second import cooldown; explicit UI review bypasses it. The authenticated local UI receives the client and end time, an opaque cue identifier, and—only when there is exactly one exact same-client match—an opaque BrainLink session reference. Matching reads session metadata only; it does not return the private summary or open transcript messages. **File summary** on a matched reminder opens the destination form and prepares a private draft preview; saving still requires the separate **Save private note** click. Changing the vault or folder invalidates the preview, which must be generated again. The client session ID, transcript path, working directory, and transcript contents are not included in the cue response. A missing or ambiguous match remains an unlinked reminder and fails closed. Run `brainlink session-end-cues` to inspect pending cues from the command line.

An optional **Local summary drafts** setting can ask the local Ollama service to prepare a draft from a matched, imported Claude Code or Codex session after its end cue arrives. The user must enable both local summaries and automatic drafting; BrainLink polls while Setup is open, handles one matching session at a time, and stores the result only in its private local draft area. It sends a bounded, secret-redacted selection of user and assistant text to the fixed loopback Ollama address. The AI-generated result is unverified. The user must preview it, choose the destination, and explicitly save it; a failed or unavailable local model creates no vault note. This optional draft path does not apply to DeepSeek Harness end events.

Validation: `test/session-hooks.test.mjs` checks merge/disable preservation, backups, idempotent installation, malformed-file refusal, authenticated controls, explicit boolean selection, and actual shell execution of generated commands over fictional data, including paths with spaces. `test/session-end-cue.test.mjs` checks minimal event storage, duplicate deliveries, private-field exclusion, exact unique same-client matching, an opaque session reference, private-summary withholding before the explicit review request, authenticated UI listing and retained dismissal. Browser review in an isolated fictional vault checked enable, trust guidance, dismissal and layout. See [UI evidence](evidence/session-closeout-ui.png). This does not replace a live client lifecycle test. Rollback: disable reminders in Sessions before reverting the change; saved cue records remain local.

### DeepSeek Harness lifecycle boundary research (2026-10-28)

BrainLink's DeepSeek Harness connector configures a local stdio MCP client. This lets the Harness call BrainLink tools, including the preview-first `session_close` tool, but does not observe or summarize Harness sessions. The regular Claude Code hook bridge supports `SessionStart`, prompt/tool hooks, `Stop`, and subagent hooks, but not Claude Code's `SessionEnd` event. `Stop` is a per-turn boundary and must not be treated as a completed conversation. Current Harness documentation describes a separate experimental Claude Code Mods bridge with a `session.end` event for a root agent; that event is distinct from core `session/disposed`, which can also happen during publication rollback. The release notes describe the mods bridge as experimental compatibility work, not a complete practical integration, and the mods run in-process without a sandbox. BrainLink therefore does not install this hook automatically. A future opt-in integration needs a version-specific isolated test and a user-visible permission step. Until then, use the BrainLink Skill and call `session_close` at task completion; preview and explicit confirmation rules still apply.

### Hermes CLI finalized-session reminder

The Sessions screen can optionally add a Hermes shell hook to the exact profile BrainLink imports. It listens for `on_session_finalize` and accepts only `platform: cli`; it does not use Hermes's per-turn `on_session_end` event. This distinction avoids showing a closeout reminder after every assistant reply. The hook sends only the lifecycle event to BrainLink, which stores a profile-scoped opaque session reference and time locally. It ignores the working directory, profile name, model, and any extra fields, including conversation data. The reminder links only to a unique imported Hermes session from that same selected profile; transcript access still follows the user's existing private-session setting and normal review flow.

Enabling or disabling the hook edits only the selected profile's `config.yaml`, creates a backup before a change, and preserves unrelated YAML settings and hook entries. The user must enable it in BrainLink and may also need to trust the command when Hermes asks. Hermes shell hooks run with the computer user's permissions, so the UI states this before enabling. BrainLink does not read or alter Hermes's consent allowlist. Disable the reminder in Sessions to remove only BrainLink's entry. Hermes Desktop, remote profiles and gateway delivery are not claimed as verified lifecycle coverage; the current implementation filters for CLI sessions and is tied to the exact profile selected for import.

Official reference checked 2026-10-30: [Hermes Agent event-hook documentation](https://hermes-agent.nousresearch.com/docs/user-guide/features/hooks/). It distinguishes the per-turn `on_session_end` event from `on_session_finalize`, which is emitted when a CLI/TUI/gateway session is torn down; it also documents that shell hooks run with the user's full OS permissions and use a first-use consent allowlist. Hermes Agent v0.21.0 was exercised against an isolated temporary profile: its real `hermes hooks test on_session_finalize` command parsed and ran the generated hook, and the resulting cue contained only the opaque profile-scoped ID, time, and cue kind. No live user's Hermes profile was changed. This verifies the installed version's config and command path with a synthetic event; actual session teardown, first-use consent, Hermes Desktop, TUI and gateway behavior remain unverified.

### DeepSeek Harness completed-turn reminder

The opt-in Harness reminder listens to the durable `session/event` feed and creates a local closeout suggestion only when a root agent records `turn/end` with reason `completed`. It does not treat `agent/disposed` as proof that the user finished, because Harness can dispose an agent for other lifecycle reasons. A new `turn/start` clears the earlier suggestion; failed turns do not create one; Harness suggestions expire from the reminder list after 14 days. The suggestion contains only the Harness session ID, completion time, and cue type. It does not capture transcript text, and it never starts the local summary model automatically. The user can review and file it through the existing preview-first flow.

The Sessions screen offers this toggle only for a connected named Harness profile. BrainLink adds one profile-local Cordis plugin row, backs up the existing patch, preserves unrelated plugins, and removes only its own row when disabled. The plugin file remains in BrainLink's local application data because another connected profile may use it. Setup verifies that the plugin file exists and points to the current local cue folder before showing it as configured. Harness plugins run inside Harness with the same computer-user permissions; the UI says this before enabling. This is an explicit opt-in integration and still needs testing inside the user's actual Harness profile. It does not prove a live profile loaded the plugin or a model called BrainLink.

The Harness API used here is documented in the versioned [`dsh-v0.2.1-rc.3` runtime event types](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/packages/core/agent/src/runtime-types.ts), which define `session/event` and `turn/end`, and the matching [agent registry](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.3/packages/core/agent/src/index.ts), which distinguishes root agents. The Harness [Cordis plug-in guide](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/develop/basic/index.md) documents profile-local plugins and lifecycle cleanup. The local tests simulate these documented events; they are not a live Harness runtime test.

### DeepSeek Harness session import

BrainLink now includes a read-only DeepSeek Harness session importer in the same local refresh used by `brainlink sync` and the Sessions screen. It reads only the configured `DSH_HOME/sessions` folder, or `~/.dsh/sessions` when `DSH_HOME` is not set. It accepts raw JSONL and the default concatenated Zstandard-frame files for session formats v3 and v4, with a 32 MiB input and 128 MiB decoded-size limit. Other format versions and malformed logs are reported and retried later; source files are never changed.

The importer keeps only direct user prompts and visible assistant text. It skips injected user context, system/developer messages, reasoning blocks, tool calls/results, and unrelated event records, then applies BrainLink's secret redaction before storage. Imported sessions are private by default and remain hidden from connected AI clients unless the user changes the existing sharing setting. That setting applies to supported imported sources, including DeepSeek Harness; summary sharing does not reveal message excerpts, and full-text sharing remains a separate opt-in. Sessions recorded directly through `session_log` stay private under both settings. The completed-turn cue is not proof that a Harness conversation ended. If local AI summaries and automatic drafts are enabled, BrainLink waits 30 minutes, checks that no newer visible message exists, then prepares a private draft locally. It rechecks the cue after inference and never files without review and confirmation. On this Windows host, the DeepSeek Harness desktop app is present at version 44.7.0, but no live profile import was performed; verification of the importer remains fixture-based.

Validation: `test/sessions.test.mjs` checks concatenated Zstandard frames, raw v3 JSONL, idempotent refresh, redaction, privacy, and exclusion of planted injected-context, reasoning, and tool-output canaries. `test/wiring.test.mjs` checks discovery through both `brainlink sync` and MCP session listing using a fictional compressed session. `test/sessions-mcp.test.mjs` checks the user's summary/full-text sharing choices for imported Harness sessions and confirms direct `session_log` records are not relaxed. A direct installed-Harness import and its current production format still need live verification.

### Hermes Agent session import

BrainLink also imports ended Hermes CLI sessions from one selected Hermes profile’s `state.db` during local refresh. In **Settings → Sessions**, choose the profile folder that contains `state.db`, or select **Use default profile**. The default follows Hermes: `$HERMES_HOME` when set; otherwise `%LOCALAPPDATA%\hermes` on Windows or `~/.hermes` on macOS/Linux. BrainLink does not scan or combine all Hermes profiles. Switching profiles does not delete sessions already imported from the prior profile; they remain in BrainLink’s local session history and follow the existing session-sharing settings.

The importer opens the database in SQLite read-only mode and only runs on Node versions where that option is supported. It selects ended sessions tagged `cli`, then reads active `user` and `assistant` message content only. It excludes messaging sessions, open sessions, archived/compacted messages, system prompts, tool calls/results, and reasoning fields. Imported sessions are private by default and use the existing separate summary and full-text sharing choices. The importer pages sessions incrementally and bounds the imported text size. Missing or unsupported databases are skipped or reported without falling back to a writable database connection.

Synthetic database tests cover private-by-default storage, incremental paging, source immutability, redaction, and exclusion of messaging, open-session, archived, tool, and reasoning canaries. Wiring tests exercise `brainlink sync` and lazy session refresh. A desktop settings test verifies profile selection and reset, including retention of previously imported sessions. These tests do not open Ian’s live Hermes database or prove live model use.

Remaining for the complete product: local model-generated summaries are opt-in, private drafts, not verified outcomes or autonomous vault filing. The local Ollama call has fixture coverage but has not been validated with a live local model in this environment. DeepSeek Harness has a synthetic-tested completed-turn cue and 30-minute inactivity-based draft path, but its live plugin load, session import, and inference with a real local model are unverified. Live client lifecycle and Claude-to-Codex continuation, provider-measured token/time savings, and full Personal/Organisation/Client privacy acceptance also remain open. An inactivity cue or AI-reported summary alone is not a verified session end or long-term rule.
